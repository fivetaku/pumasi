# 안티패턴: 복붙형 instruction

> 품앗이에서 가장 자주 가치를 잃게 만드는 실수다.

아래 패턴이 들어가면 호스트가 이미 구현 토큰을 다 쓴 셈이라 외주의 이점이 사라진다:

```
❌ 피할 것 (이유는 아래):
- instruction에 완성된 함수/컴포넌트 코드 블록 포함
- "위 코드를 그대로 작성하세요" 패턴
- 호스트가 구현을 다 한 후 워커에게 파일 저장만 시키는 것
- JSX/HTML 마크업을 instruction에 직접 작성
- 비즈니스 로직을 코드로 제공

이런 패턴이면 호스트가 이미 토큰을 소비한 것이고,
워커는 단순 파일 저장 도구로 전락한다.
차라리 호스트가 Write 도구로 직접 쓰는 것이 더 효율적이다.
```

## 왜 이런 실수가 발생하는가?

1. 호스트(LLM)는 "과잉 친절" 성향이 있어 코드를 끝까지 완성하려 함
2. "모든 것을 명시하라"를 "구현까지 다 써라"로 오해
3. 게이트가 약하면(ls/grep만) 호스트가 불안해서 코드를 다 써버림
4. **해결: 시그니처+요구사항만 작성하고, 강한 게이트(tsc/build/test)로 검증**

## Red Flags — 자가체크표 (instruction 작성 중 점검)

> 출처: obra/superpowers의 합리화 차단표 패턴. PM(호스트)이 역할을 이탈하기 **직전의 생각**을 잡아낸다.
> instruction을 쓰다가 아래 생각이 떠오르면 잠시 멈추고, 시그니처+요구사항+게이트만 남기는 쪽으로 고친다.

| 이런 생각이 들면 (충동) | 현실 |
|------------------------|------|
| "이건 내가 직접 짜는 게 더 빠르겠는데" | 그 순간 토큰 절약 = 0, 워커가 파일 저장 도구로 전락. 품앗이 존재 이유 위반 |
| "body 한 줄인데 그냥 써주자" | 한 줄이 두 줄 되고 곧 함수 전체가 되기 쉽다. 시그니처에서 멈추는 편이 낫다 |
| "이 로직은 복잡해서 설명보다 코드가 명확함" | 복잡할수록 워커에게 맡길 가치가 크다. 요구사항과 테스트 게이트로 풀어 쓴다 |
| "워커가 못 알아들을까 봐 불안함" | 불안의 해법은 코드 대필이 아니라 **강한 게이트**(tsc/build/test) |
| "JSX/마크업 정도는 내가 빨리..." | 렌더링 로직도 구현이다. 구조·props만 명시하고 body는 워커 몫 |

이 생각들은 모두 호스트가 구현자 역할로 넘어가고 있다는 신호다. 역할 경계(role-separation.md)를 다시 확인한다. 작업이 작아서 직접 쓰는 게 정말 낫다면 품앗이 대신 직접 코딩하는 것이 맞다.

문구만 지키고 의도를 어기는 경우도 같다 — 주석에 완성 코드를 숨기면 결국 구현을 대신 쓴 것이다.
