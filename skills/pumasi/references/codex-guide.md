# 워커 instruction 작성 가이드 (Codex 포함)

요즘 코딩 워커는 맥락 추론과 구현을 모두 잘한다. 약한 것은 **호스트 머릿속에만 있는 결정**이다 — 어떤 시그니처를 다른 태스크가 기대하는지, 어떤 라이브러리를 써야 하는지, 언제 끝난 것인지. instruction은 그 결정을 전하고, 끝남은 게이트로 정의한다.

## instruction에 넣을 것

- 목표: 무엇을 만들거나 고치는지, 왜 필요한지 한두 문장
- 다른 태스크와 맞물리는 시그니처·타입 (body 없이)
- 꼭 써야 하는 라이브러리 — 지정하지 않으면 워커가 더 쉬운 방법(예: DB 대신 JSON 파일)으로 바꿀 수 있다
- 고칠 파일·읽기만 할 파일 (task의 `files`·`read_only` 필드로 주면 프롬프트에 따로 표시된다)
- 금지사항과 그 이유

경로는 작업 디렉토리 기준 상대 경로면 충분하다. 워커 프롬프트에 작업 디렉토리가 같이 들어간다.

## 넣지 않을 것

- 함수·컴포넌트 본문, 마크업, 비즈니스 로직 구현 — 호스트가 쓰면 외주로 아끼려던 토큰이 그대로 나간다
- 설정 파일 전체 — 핵심 설정값만 준다
- 프로젝트와 무관한 일반 스타일 규칙 — 프로젝트 관례가 있으면 워커가 따르고, 따로 정할 것은 config `style`에 둔다

짧은 예시 코드(호출 형태, import 한 줄)는 시그니처를 설명하는 데 필요하면 넣어도 된다. 기준은 길이가 아니라 "구현을 대신 써 주고 있는가"다.

## 라이브러리 대체를 막는 법

코드를 주지 말고 제약사항과 게이트를 준다.

```yaml
instruction: |
  src/db.ts에 better-sqlite3 기반 저장소를 만든다 (JSON/fs 저장은 쓰지 않는다 — 동시 쓰기 안전성이 필요하다).
gates:
  - name: "better-sqlite3 사용 확인"
    command: "grep -q 'better-sqlite3' src/db.ts && ! grep -q 'readFileSync' src/db.ts"
  - name: "타입 체크"
    command: "npx tsc --noEmit"
```

게이트 명령은 워커 프롬프트의 "완료 기준"에 그대로 들어가고, 워커가 직접 실행해 통과시킨 뒤 보고한다. 호스트도 같은 명령으로 다시 판정한다.
